# telegram-mika-relay

Hermes carries the Telegram binding for this workspace as **transport**. It is not
gabriele.vadala's conversational counterpart — Mika is. This plugin makes that
true in code: an inbound Telegram message is deposited on a Multica issue
assigned to Mika, and Mika's reply is what comes back on the channel.

Before this plugin, every Telegram reply was generated by Hermes's own agent loop
(it introduced itself as "Claude Code"). That was not a routing bug — no relay
code existed anywhere. See VDLP-16.

## How it works

```
Telegram DM
    │
    ▼
pre_gateway_dispatch hook  (__init__.py)          ← runs BEFORE auth/agent dispatch
    │  utility command (/status, /new …)? → None → Hermes answers locally
    │  otherwise → multica issue comment add → {"action": "skip"}
    ▼                                               (Hermes's agent loop never runs)
Multica issue assigned to Mika
    │
    ▼
Mika's run posts a comment
    │
    ▼
relay_poller.py --loop  (systemd user service)
    │  multica issue comment list --since
    ▼
hermes send --to telegram:<chat_id>
```

### The three design decisions (approved on VDLP-16)

1. **Mapping — one persistent issue per chat, reused.** Not one issue per
   message: a Telegram conversation is a continuous thread, and N issues drown
   the board and lose the context that makes it readable. The
   `chat_id → issue_id` map lives in
   `$HERMES_HOME/telegram-mika-relay/chat_issue_map.json`, on disk, so it
   survives a gateway or host restart. A `done`/`cancelled` issue is reopened
   rather than replaced — unless it has been closed longer than
   `STALE_REOPEN_SECONDS` (7 days), past which resuming the thread would read as
   a non-sequitur appended to settled work, and a new issue is opened instead.

2. **Round-trip — asynchronous.** The hook enqueues and returns; a separate
   poller delivers. Synchronous would hold the gateway turn open for the whole
   duration of Mika's run (minutes on a non-trivial issue), showing the user
   nothing and risking a timeout that loses the message. Multica exposes no
   outbound "agent commented on issue X" primitive, so the return path polls
   `multica issue comment list --since`.

3. **Scope — everything is relayed except an explicit list of utility commands.**
   `LOCAL_COMMANDS` in `__init__.py` names them (`/status`, `/new`, `/model`, …);
   they are channel controls and make no sense as issues. The rule is the list,
   never a heuristic on the content — a heuristic guesses wrong eventually, and
   it fails in the worst direction: silence.

### Failing open, loudly

If Multica is unreachable the user's message **must not disappear**. Returning
`{"action": "skip"}` after a failed relay is the worst possible outcome: the user
wrote, nobody answered, nobody knows. Instead the plugin:

1. reports the failure on the channel with the verbatim error, and
2. returns `None`, so Hermes's own agent loop answers — the pre-VDLP-16 path,
   subordinated rather than deleted.

A crash inside the hook does the same thing.

## Install

```bash
cp -r hermes-plugins/telegram-mika-relay ~/.hermes/plugins/telegram-mika-relay
hermes plugins validate ~/.hermes/plugins/telegram-mika-relay
hermes plugins enable telegram-mika-relay
hermes gateway restart          # hooks load at gateway start

# return path
mkdir -p ~/.config/systemd/user
cp ~/.hermes/plugins/telegram-mika-relay/systemd/telegram-mika-relay.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now telegram-mika-relay.service
loginctl enable-linger "$USER"  # so the poller survives a reboot
```

The poller runs as a **systemd user service** rather than a cron job: it must
come back by itself after a host restart (`Restart=always` + `enable` +
linger), and a service keeps exactly one instance, so two overlapping passes can
never deliver the same comment twice.

## Kill switch

Back to the previous behaviour in one command, without uninstalling anything:

```bash
touch ~/.hermes/telegram-mika-relay.disabled     # hook + poller both idle
rm ~/.hermes/telegram-mika-relay.disabled        # back on
```

`HERMES_TELEGRAM_MIKA_RELAY=off` does the same for the hook.

## Never delivering twice

`delivered.json` holds the set of comment ids already sent plus a per-issue
`--since` cursor, both on disk. Every pass checks the id set first, so an
overlapping re-read is harmless. A comment whose send **fails** is deliberately
not recorded — it is retried on the next pass rather than silently dropped.

The relay's own inbound copies are recognised by the `Inoltrato da
Operator(Hermes)` marker and never echoed back to the chat that produced them.

### Why the issue is created `backlog`, not `todo`

Creating a `todo` issue already assigned to Mika dispatches a run immediately,
and the relay comment posted right after dispatches a second one — the user gets
answered **twice** on Telegram for one message. Observed live on VDLP-34.
Creating the issue parked makes the first relayed comment the single trigger.

```bash
python3 -m pytest hermes-plugins/telegram-mika-relay/tests -q
```
