# MetaMCP — the single authenticated endpoint

MetaMCP aggregates the FirecREST tool into one MCP endpoint, so Hermes (prompt 05)
is configured with exactly one tool source instead of one per tool. See
`ARCHITECTURE.md` → "One authenticated endpoint, not N tool integrations".

## Endpoint

| | |
|---|---|
| Endpoint URL | `http://localhost:12008/metamcp/firecrest-workbench/mcp` |
| Transport | Streamable HTTP |
| Authentication | API key, sent as `Authorization: Bearer <key>` |
| Namespace | `firecrest-workbench` (namespace uuid `c7ad0d9a-76e6-4461-ac19-b65e3ed8bc1c`) |
| UI | `http://localhost:12008` |
| Admin UI login | see `.secrets/metamcp-admin-password.txt` (gitignored) |

Verified: a request without an API key gets **HTTP 401**; with the key it gets 200 and
the `initialize` handshake succeeds.

## Where the API key lives

```
.secrets/metamcp-api-key.txt      # gitignored, mode 600
```

**No API key is committed to this repository.** The key is generated by MetaMCP at
bootstrap and stored in plaintext in the `api_keys` table of MetaMCP's Postgres —
readable with `scripts/read_metamcp_api_key.sh`, which writes it to the path above
without printing it.

## Tools exposed

Exactly five, all from the FirecREST MCP wrapper (prompt 02), renamed with the
server prefix MetaMCP applies:

```
firecrest__submit_job
firecrest__get_job_status
firecrest__list_files
firecrest__download_file
firecrest__get_job_log
```

MetaMCP's own ~51 administrative tools (`metamcp-admin__*`) are **deliberately
disabled** on this endpoint. They appear whenever the endpoint's
`enable_metamcp_admin_tools` flag is on, and enabling it would hand the agent in
prompt 05 full control over MetaMCP's configuration — which `ARCHITECTURE.md`
explicitly rules out ("the hackathon demo agent should not have access to anything
beyond the FirecREST/DocMind namespace"). They are switched on temporarily when
configuration has to be changed, then switched off again; see below.

## How it is configured, and why not the obvious way

### The published image cannot be configured headlessly

`ghcr.io/metatool-ai/metamcp:latest` is **v2.4.22** (revision `32b6e98`, December
2025) and predates the `BOOTSTRAP_*` environment variables that exist on `main`.
The compiled backend in that image contains **zero** occurrences of `BOOTSTRAP_ENABLE`
or any sibling: bootstrap, users, API keys, namespaces and endpoints all have to be
created by hand in the web UI.

This instance therefore builds from source. `docker-compose.override.yml` points the
`app` service at a local build (`metamcp-local:dev`) and leaves the upstream
`docker-compose.yml` untouched so it stays diffable.

### Bootstrap configuration

`scripts/make_metamcp_env.py` generates `metamcp/.env` from upstream's `example.env`,
replacing the placeholder secrets with generated ones and appending a declarative
bootstrap block: one admin user, one API key, the `firecrest-workbench` namespace,
and the endpoint. Secrets are generated and written, never printed.

### Two ordering traps in the bootstrap

Both were hit while building this, and both are worth knowing before repeating it:

1. **Registration controls are applied before the bootstrap user is created, and the
   user is created through the sign-up endpoint those controls gate.** With
   `BOOTSTRAP_DISABLE_REGISTRATION_UI=true` the run logs
   `Registration controls set: UI=false`, then
   `ERROR [Better Auth]: Failed to create user — New user registration is currently
   disabled`, then `Skipping API key "firecrest-workbench" because user ... was not
   found`. One failed user silently costs you the API key, the namespace ownership and
   the endpoint. Leave registration enabled during the first boot and disable it
   afterwards.
2. **Bootstrap cannot attach MCP servers to a namespace, and cannot enable the admin
   tools.** `EndpointConfig` in `bootstrap.service.ts` accepts `enable_auth`,
   `enable_auth_query` and `enable_auth_oauth` but not `enable_metamcp_admin_tools`,
   and there is no `BOOTSTRAP_MCP_SERVERS`. Attaching a server is a separate step.

### Attaching the FirecREST server

Because bootstrap cannot do it, the server is registered through MetaMCP's own admin
MCP tools — `scripts/metamcp_admin.py add-firecrest`:

1. `metamcp_create_mcp_server` with `type=STREAMABLE_HTTP` and
   `url=http://host.docker.internal:8765/mcp`. That hostname works unmodified: the
   upstream compose already declares
   `extra_hosts: ["host.docker.internal:host-gateway"]`, and the firecrest-mcp HTTP
   server listens on the host.
2. `metamcp_update_namespace` with `mcpServerUuids`, to add it to the namespace.
   Note `metamcp_update_namespace_server_status` looks like the right tool and is not:
   it updates the status of an *existing* membership and answers
   `"Server not found in namespace"`.

Admin tool inputs use **camelCase** (`namespaceUuid`, `mcpServerUuids`,
`serverUuid`) because they take the tRPC input shapes, not the database column names.
`metamcp_refresh_namespace_tools` is a red herring for this purpose: it expects the
caller to pass the tools it has already discovered, which is the web UI's job.

## Rotating the API key

The admin tools are required, so this is a deliberate two-step dance:

```bash
# 1. reveal the admin tools on the endpoint (temporarily)
docker exec metamcp-pg psql -U metamcp_user -d metamcp_db \
  -c "update endpoints set enable_metamcp_admin_tools = true where name='firecrest-workbench'"

# 2. create a replacement key, note the new value, then delete the old one
cd ~/Sviluppo/firecrest-agentic-workbench
firecrest-mcp/.venv/bin/python scripts/metamcp_admin.py \
  call metamcp-admin__metamcp_create_api_key '{"name":"firecrest-workbench-2"}'
firecrest-mcp/.venv/bin/python scripts/metamcp_admin.py \
  call metamcp-admin__metamcp_delete_api_key '{"name":"firecrest-workbench"}'

# 3. store the new value and put the endpoint back as it was
#    (update .secrets/metamcp-api-key.txt, then:)
docker exec metamcp-pg psql -U metamcp_user -d metamcp_db \
  -c "update endpoints set enable_metamcp_admin_tools = false where name='firecrest-workbench'"
```

The key is also visible in the UI under API Keys, which is the path to prefer if the
admin tools are off and you would rather not turn them on.

## Operating it

```bash
cd ~/Sviluppo/metamcp
sg docker -c "docker compose up -d"      # app + postgres
sg docker -c "docker compose down -v"    # also drops the database

# smoke-test the aggregated endpoint end to end
cd ~/Sviluppo/firecrest-agentic-workbench
firecrest-mcp/.venv/bin/python scripts/metamcp_e2e_test.py
```

The endpoint's behaviour depends on two other things being up: the FirecREST demo
stack (prompt 01) and the firecrest-mcp HTTP server:

```bash
cd ~/Sviluppo/firecrest-agentic-workbench/firecrest-mcp
.venv/bin/python server.py --transport http --host 0.0.0.0 --port 8765
```

## Upstream defects found while building this

Worth reporting; each one cost real time.

1. **The published image is far behind `main`** and lacks the entire bootstrap
   feature. Either publish a matching image or say so in the README.
2. **The Dockerfile hardcodes a pnpm store path** containing React's version
   (`next@15.5.12_react-dom@19.1.2_react@19.1.2__react@19.1.2`). React is at 19.2.4 in
   the lockfile, so that path no longer exists and the `sed` that raises Next's proxy
   timeout fails the build.
3. **`pnpm install --prod` in the runner stage aborts without `CI=true`**
   (`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`).
4. **`pnpm add` after `pnpm install --prod` cannot work.** Plain, it dies with
   `ERR_PNPM_INCLUDED_DEPS_CONFLICT`; with `--prod` it clears the error but leaves
   `drizzle-kit` unlinked from `apps/backend/node_modules/.bin`, and the container then
   fails at startup with `Command "drizzle-kit" not found`. Promoting the dependency
   in `package.json` before a single install is the way through.
5. **The runner stage does not copy `pnpm-lock.yaml`**, so `pnpm install --prod`
   resolves production dependencies without a lockfile. The image's dependency set is
   therefore not the one that was tested.
6. **Bootstrap ordering bug**: registration controls are applied before the bootstrap
   user is created, and user creation goes through the gated sign-up endpoint.

Fixes 2–4 are carried as commented patches in `metamcp/Dockerfile`. The clone is
gitignored; the patches are reproduced verbatim in
`docs/reports/03-metamcp-setup.md` so they are not lost with it.
